## Что проверяют unit tests

- Генерация/сохранение пароля и private permissions конфигурации.
- Чтение dotenv как данных, без исполнения shell expressions.
- Проверка порта, разных имён volumes, вывод dry-run без секрета.
- Повторный deploy без пересборки и замены существующего здорового контейнера.
- Ручной start/stop без пересоздания; отключение legacy restart policy; отказ от изменения чужого контейнера и от установки при start отсутствующего контейнера.
- Запуск всех восьми POSIX-обёрток через `sh` из другого рабочего каталога с сохранением аргументов, включая пробелы.
- Отказ от изменения чужого контейнера.
- Сборка нового образа до остановки старого; сохранение старого при build failure.
- Rollback при health failure и восстановление запуска при rename failure.
- Возврат приложения после ошибки backup.
- Проверка checksums и path traversal архивов.
- Отказ от перезаписи непустых volumes и существующего `.env`.
- Экспорт исходников без `.env`/`auth.json`; наличие manifest; блокировка при нахождении живого web-пароля в исходниках.

## Ограничения проверки

Установка Docker через apt на чистой Ubuntu/Debian и полная сборка обновлённого Dockerfile на втором сервере здесь не выполнялись. Новый Dockerfile использует lock того же проверенного набора Python-пакетов. Автоматический rollback проверен unit tests; backup/restore дополнительно проверен с настоящим Docker. ARM64 кодом поддержан, но образ для ARM64 не собирался. Браузерные visual tests на этом VDS не запускались из-за ограниченной памяти.

После установки на новом сервере нужно проверить healthcheck, открыть интерфейс в браузере, выполнить вход в Codex и запрос к доступной модели. Эти проверки входят в инструкцию [развёртывания](DEPLOYMENT.md).

## Проверка ручного режима

`tests/integration-manual.py` запускает временный web-контейнер без production volumes и опубликованных портов. Проверяет старт остановленного контейнера, healthcheck, перевод `unless-stopped` в `no`, повторный start без изменения времени запуска и повторный stop. Лимит тестового контейнера: 96 МБ и 0.5 CPU, healthcheck с интервалом две секунды. Более строгий пробный лимит 64 МБ/0.25 CPU не уложился в timeout healthcheck; после настройки достаточных тестовых ресурсов проверка прошла. Тестовый контейнер удалён. Рабочая ОС для проверки не перезагружалась; отключение автозапуска подтверждено сохранённой Docker restart policy `no`.

## Проверка совместимости с sh

После исправления обёрток прошли 27 unit tests, включая запуск всех восьми обёрток через POSIX `sh` из другого каталога. На текущем сервере успешно выполнены `sh ./scripts/status.sh` и повторная остановка через `sh ./scripts/stop.sh`. Реальный lifecycle-тест временного контейнера также прошёл с новым Docker flag `--timeout`, без предупреждения об устаревшем `--time`. Рабочий сервис оставлен в остановленном владельцем состоянии.

## Проверка отображения статуса

После исправления сохранённого health остановленного контейнера прошли 31 unit test: для stopped/paused health равен `null`, для running остаётся текущим, отсутствие healthcheck допускается. Команда на текущем сервере показала `status=stopped`, `running=false`, `health=null`, `restart=no`. Проверка не меняет состояние контейнера.
